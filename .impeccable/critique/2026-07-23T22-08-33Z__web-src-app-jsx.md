## Design Specificity Verdict

**LLM assessment:** This clears the "could be any dashboard" bar convincingly on first read — monospace numerals throughout, three disciplined trace hues, threshold bands drawn as real geometry at 5%/10% with stamped labels, a one-time pen-draw reveal instead of a loop, no shadows/gradients/pill buttons, a single scrolling instrument layout instead of sidebar+cards. It reads as authored for watching risk rails against real-time series, not a generic admin panel with a dark theme applied.

Specificity erodes in exactly one place: the "Show feature / risk / data settings" panel. There, the Strip Recorder identity is carried by font/color tokens alone, not by composition — plain labeled-input grids that could belong to any settings form. The Reserved-Channel violation there (next section) is the concrete symptom of the signature system not being carried all the way through.

**Deterministic scan:** The mechanical detector (`detect.mjs`) found one issue on a full scan of `web/src`: a `layout-transition` warning at `components/features/feature-usage-chart.css:38` — `.feature-usage-chart__bar` animates `width` directly (`transition: width var(--duration-normal)...`) instead of a compositor-only `transform: scaleX()`, which is exactly the animation-property mistake this project's own coding-style rules warn against. Low severity on its own, but it lands in the same file as the Reserved-Channel violation below — the Alpha Feature Blocks widget is this dashboard's one component that didn't get the same craft pass as everything else.

**Visual/browser evidence:** No user-visible overlay was left running in the browser — only an injection preflight was performed (setting `document.title` and appending a `<script>` tag both succeeded, confirming overlay injection would work if run), per this review's scope. Live screenshots at desktop and 768px widths confirmed the "no shadows/gradients/pill buttons" claim directly. Narrower-than-768px resize was unreliable in the browser tool this session, but cross-referencing the actual CSS shows the real gap precisely: `styles/tokens.css`, `metrics-panel.css`, `job-console.css`, `risk-panel.css`, `feature-panel.css`, `action-panel.css`, `instrument-bezel.css`, and `run-list.css` all have **zero** `@media` rules — the narrowest breakpoint anywhere in the codebase is 700px (`live-panel.css`), meaning nothing has been explicitly adapted below phone-tablet width.

## Overall Impression

The core instrument — the Channel Strip, the threshold bands, the metrics panel, the run comparison — is genuinely excellent and rare: a design system's signature idea (drawn geometry proving the risk rails are real and binding) survived all the way into working, on-brand code. The weak spot is entirely in the layer built most recently and fastest: the advanced settings panel and the Live Trading tab. That's also the layer with the highest financial stakes, which is the real problem — the parts of this product where a mistake costs the most money are the parts that got the least design attention.

## What's Working

1. **The Channel Strip component delivers the product's core promise.** Threshold bands render as real geometry positioned at literal risk values (DRAWDOWN WARN 5% / KILL-SWITCH 10%) with stamped labels, tabular-numeral ticks, and a one-time pen-draw reveal — not a loop, not a badge. This is the rare case where a design system's stated thesis and the shipped code are the same thing.
2. **The live-arm gate is enforced server-side, not just in the UI.** `jobs_routes.py` independently checks the port isn't 7497 and mirrors `run_live.py`'s own `--live` guard — a UI bug can't accidentally arm real trading. Real defense in depth for a tool where the UI and the trader are the only two parties in the loop.
3. **Comparison mode and the actual-vs-predicted overlay are implemented exactly to spec and are genuinely useful, non-generic analytical features** — ghosted second-run traces at 40% opacity in the same channel color, walk-forward price reconstruction — the kind of thing a template dashboard would never have.

## Priority Issues

**[P0] Risk and feature configuration silently does not apply to Paper or Live trading, and nothing in the UI says so.**
- **Why it matters**: `RiskPanel`/`FeaturePanel` overrides are wired only into `startBacktest`/`startOptimize` (`ActionPanel.jsx`'s `structuralPayload()`). `startPaper`/`startLive` send only `tickers/host/port/client_id/confirm` — `PaperJobRequest`/`LiveJobRequest` don't even have `features`/`risk` fields, and `run_live.py`'s CLI has no `--params` flag (hardcoded `params=None`, with a comment telling the *developer* to edit source). A user who tightens the kill-switch to 3% in the Backtest tab and then switches to Live Trading has every reason to believe that setting is still active. For a product whose entire design thesis is "prove the risk rails are real, live, and binding," this is the one path where that claim is currently false and invisible.
- **Fix**: At minimum, render the actual (hardcoded) risk rails read-only on the Paper/Live tabs with an explicit label ("risk rails for this run: fixed defaults, not the values configured above") — or wire the override plumbing through `run_live.py` so it's actually true.
- **Suggested command**: `/impeccable harden`

**[P1] Reserved-Channel Rule violation: Trace Cyan and Violet reused as generic UI-state colors.**
- **Why it matters**: `feature-usage-chart.css` (lines ~46-53, ~60-65) uses `--color-trace-cyan` for "FIT" state and `--color-trace-violet` for "RAW" state in the Alpha Feature Blocks widget — a settings panel, not the ML-performance or regime channels those hues are reserved for. This is the exact failure DESIGN.md names by name: "the moment a color's meaning becomes ambiguous, the instrument stops being legible at a glance." A user who has learned "cyan = ML performance" now also sees cyan mean "fit-mode" in an unrelated widget.
- **Fix**: Use a neutral pair (text-primary/text-dim, or a new non-reserved accent) for fit/raw/off state in `FeatureUsageChart`.
- **Suggested command**: `/impeccable polish`

**[P1] Job Console list items clip/overflow, and the console has zero responsive breakpoints — confirmed independently by both the design review and live DOM inspection.**
- **Why it matters**: Both assessments hit this without seeing each other's work — the strongest kind of finding. Live screenshots at 500px and 768px both show job rows cut off mid-word (e.g. "...02:56 P" with the "M" sliced off). DOM measurement confirms it: `.job-console__item` `scrollWidth: 284` vs `clientWidth: 261` (23px overflow) inside a fixed `280px` grid column (`job-console.css:3`), with no `min-width: 0`/ellipsis handling on `.job-console__item-name`/`-time`. `job-console.css` and `action-panel.css` (home of the safety-critical 320px-min confirm-phrase field) both have zero `@media` rules, unlike `App.css`/`channel-strip.css` which already have an 1024px pattern to copy.
- **Fix**: Add `text-overflow: ellipsis` + `min-width: 0` to `.job-console__item-name`/`-time`, and extend the existing 1024px breakpoint pattern to `job-console.css` and `action-panel.css`.
- **Suggested command**: `/impeccable adapt`

**[P1] Live-arm confirm field's placeholder is not visually distinguished from real input — at the highest-stakes moment in the product.**
- **Why it matters**: No `::placeholder` rule exists anywhere in the stylesheets; the confirm-phrase `<input>` inherits full `text-primary` color, so the browser default is the only thing dimming placeholder text. Screenshots show the placeholder rendering at essentially the same brightness as genuinely-typed adjacent values. This is the one field gating deployment of real capital, and at a glance — especially DESIGN.md's own invoked "2am" scenario — it can read as already-satisfied.
- **Fix**: Add `.action-panel__confirm-input::placeholder { color: var(--color-text-dim); opacity: 0.6; font-style: italic; }`.
- **Suggested command**: `/impeccable polish`

**[P2] Metrics panel applies semantic color inconsistently.**
- **Why it matters**: Only `net_profit_usd` is color-coded by sign in `MetricsPanel.jsx`'s `ROWS` config; Sharpe (-0.31) and Sortino (-0.23) render in plain white, visually identical to a good value. On a screen whose entire premise is "read risk state at a glance," two of the most important risk-adjusted-return numbers being indistinguishable from "fine" when they're bad undermines the instrument-panel metaphor.
- **Fix**: Extend sign-based coloring to Sharpe/Sortino/Profit Factor and any other metric with a meaningful positive/negative zero-point.
- **Suggested command**: `/impeccable polish`

## Persona Red Flags

**Alex (Power User)**: Hits the Alpha Feature Blocks chart-plus-form duplication immediately (`FeaturePanel` renders `FeatureUsageChart` directly above a form controlling the identical four values) and finds it slows a loop that should be fast — noise for someone who already knows what `n_lags`/`regime_source` mean. Alex is also the persona most likely to get burned by the P0 issue above: exactly the user sophisticated enough to tune the risk panel before going live, and therefore exactly the user most misled by it silently not applying.

**Sam (Accessibility)**: The tab buttons (Run Backtest / Start Optuna Sweep / Paper Trading / Live Trading) have no `role="tab"`/`aria-selected` — active-mode is conveyed by color alone. Confirmed via live accessibility snapshot: the "ML / Regime channel ticker" `<select>` in `App.jsx:130-140` has no `id`, `name`, `aria-label`, or wrapping `<label>` (just a sibling `<span>`) — a screen reader announces only "BTC, combobox" with zero indication of what it controls, unlike the adjacent "Asset Class" select which does expose a proper accessible name.

## Minor Observations

- Run identifiers are opaque hex (`optimize_6b95f5ee7f`) everywhere they're surfaced; a human label (tickers + timestamp, already computed elsewhere) in `MetricsPanel`'s title would cut the "which run is this" recall burden.
- `RunList`'s disabled "compare" button on the active run has no visible explanation for why it's disabled.
- Raw `err.message` from caught fetches surfaces verbatim in `ActionPanel` — a bit of domain-specific messaging for the likely-common "IBKR/TWS not reachable" case would help.
- The mechanical detector's one finding (`feature-usage-chart.css:38`, animating `width` instead of `transform: scaleX()`) lands in the same file as the P1 color-reuse issue above — the Alpha Feature Blocks widget is the one component that didn't get the same craft pass as the rest of the app.
- 27 browser console "form field element should have id or name" notices were observed, but on inspection only the ticker `<select>` above is a real accessible-name defect — the rest are label-wrapped inputs, an autofill/best-practice nit rather than a broken screen-reader experience.
